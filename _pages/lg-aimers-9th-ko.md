**활동 기간: 2026.08.05~2026.09.02 · 역할: 팀장 · 성과: 63위**

## 투구 전에 알 수 있는 정보로 성공 가능성을 예측하기

LG Aimers 9기 온라인 해커톤에서 떡잎마을방범대 팀의 팀장을 맡았습니다. 과제는 경기 상황과 선수의 과거 이력을 바탕으로 다음 투구의 제구 성공 확률을 예측하는 것이었습니다. 이미 던진 공의 위치로 성공 여부를 판정하는 문제가 아니라, 투구 전에 이용할 수 있는 정보만으로 확률을 추정해야 했습니다.

팀은 야구 경기 상황과 선수 이력을 이해하는 것부터 시작해 데이터 Preprocessing과 Feature Engineering, 단일 모델 비교, Ensemble 실험을 진행했습니다. 저는 팀원들의 일정 관리, Notion을 통한 보고서와 문서 관리, 회의 주관, 코드 점검과 개선 의견 제시를 맡아 프로젝트 전체의 진행을 조율했습니다.

## 팀장으로 맡은 일

여러 모델을 동시에 실험하다 보니 팀원별 진행 상황을 파악하고 결과를 공유할 필요가 있었습니다. 한 팀원의 예측 결과가 다른 팀원의 Ensemble 실험에 쓰이기도 했습니다. 저는 팀원들의 일정을 확인하고, 회의와 Notion 문서를 통해 진행 상황을 공유했습니다.

| 담당한 일 | 실제 활동 |
|---|---|
| 일정 관리 | 팀원별 일정을 확인하고 전체 진행을 조율 |
| 문서 관리 | Notion에서 보고서와 프로젝트 문서를 관리 |
| 회의 주관 | 진행 상황과 실험 결과, 추가로 검토할 내용을 논의 |
| 코드 검토 | 팀원들의 코드를 점검하고 개선 방향에 대한 의견 제시 |
| 프로젝트 진행 | 개별 작업을 살피며 프로젝트 전반의 흐름 관리 |

코드를 검토할 때는 이전 실험에서 무엇을 바꿨고 그에 따라 결과가 어떻게 달라졌는지 확인했습니다. 이를 바탕으로 개선 의견을 제시하고, 회의에서 다음에 시도할 방법을 함께 논의했습니다.

## 야구 도메인을 이해하고 예측에 쓸 정보 구분

먼저 볼·스트라이크 카운트, 아웃, 주자 상태, 점수 차가 어떤 경기 상황을 뜻하는지 살폈습니다. 같은 선수라도 상황에 따라 제구 성공 확률이 달라질 수 있어, 선수의 과거 평균과 현재 경기 상황을 함께 고려했습니다.

선수 이력은 수치의 크기만으로 해석하기 어려웠습니다. 성공률이 같더라도 관측 횟수가 적은 선수와 충분한 기록이 있는 선수의 정보를 같은 정도로 신뢰할 수는 없었습니다. 기록이 없는 선수와 기록은 있지만 성공률이 낮은 선수도 구분해야 했습니다. 최근 1·3·5경기 기록과 장기 기록을 비교하며 최근 상태 변화가 추가 정보를 주는지 살폈습니다.

예측 시점도 중요했습니다. 현재 투구의 위치나 결과처럼 투구가 끝난 뒤 알 수 있는 값은 입력에서 제외하고, 투구 전에 확인할 수 있는 경기 상황과 과거 누적 기록만 사용했습니다. main 데이터와 TrackMan 데이터는 선수 ID 체계가 달라 같은 숫자라는 이유로 바로 연결하지 않았습니다.

## 데이터 Preprocessing과 Feature Engineering

결측값을 처리할 때는 이력 유무와 관측 횟수를 함께 사용해 정보가 없는 상태를 구분했습니다. 범주형 입력에서는 드물게 등장하는 ID를 묶고, 학습 때 보지 못한 ID를 별도로 처리하는 방법을 실험했습니다. 통계값과 범주 사전은 각 Validation fold의 학습 데이터에서 정하고, 같은 설정을 검증 데이터에 적용했습니다.

Feature Engineering에서는 도메인에서 세운 가설을 입력으로 표현하고 실제 예측에 도움이 되는지 비교했습니다.

| Feature 묶음 | 구성과 비교한 내용 |
|---|---|
| 선수의 장기·시즌 이력 | 투수·타자의 과거 성공률과 누적 관측 수를 함께 사용하고, 표본이 적을 때 기준 확률 쪽으로 보정 |
| 최근 상태 | 직전 1·3·5경기 기록과 장기 성공률의 차이로 최근 변화 표현 |
| 경기 상황 | 볼·스트라이크 조합, 아웃, 주자 상태와 점수 차 반영 |
| 상대 조합 | 투타 좌우 조합과 팀·상대 팀 정보를 활용한 상호작용 검토 |
| 이력의 신뢰도 | 이력 유무, 표본 수, 최근 기록의 가용성으로 입력 정보의 양 표현 |

Feature를 추가한다고 항상 성능이 좋아지지는 않았습니다. 팀은 Feature 묶음을 더하거나 줄여 결과를 비교했고, 한 모델에서 효과가 있었던 구성이 다른 모델에서도 유효한지 확인했습니다. 예를 들어 DCN에서 고른 축소 Feature를 CatBoost에 적용했을 때 전체 평균은 개선됐지만 일부 연도에서는 오히려 성능이 낮아져 채택하지 않았습니다.

## 단일 모델별 실험과 비교

CatBoost, LightGBM, XGBoost와 함께 FT-Transformer, RealMLP, SAINT 등 정형 데이터용 Deep Learning 모델을 실험했습니다. 모델 이름만 바꾸어 점수를 비교하기보다, 같은 계열 안에서 입력과 학습 방식이 예측에 미치는 영향을 살폈습니다.

| 모델 계열 | 주요 실험 |
|---|---|
| CatBoost·LightGBM·XGBoost | 확률 직접 예측과 Residual Learning, 최근 시즌 가중치, 드문 범주의 통합, Feature 구성 비교 |
| FT-Transformer | 선수 이력 기반 기준 확률을 입력으로 제공하거나, 그 확률에 제한된 보정값을 더하는 방식 비교 |
| RealMLP | 경기 상황과 최근 상태 Feature, 기준 확률, Tree-based 모델의 예측을 결합하는 방식 비교 |
| SAINT | Feature 간 Attention과 평가 행 사이의 Attention이 예측에 미치는 영향 검토 |

선수 이력으로 만든 기준 확률을 모델이 처음부터 다시 예측하게 할지, 기준이 놓친 오차만 보정하게 할지도 비교했습니다. 모델이 복잡해지거나 입력이 늘어나는 것 자체보다, 기존 기준에 없던 정보를 실제로 활용하는지가 중요했습니다.

## Temporal Validation과 월별 보정 검토

팀이 시도한 월별 보정은 시즌이 진행되면서 선수의 상태와 경기 양상이 달라질 수 있다는 생각에서 출발했습니다. 월에 따라 보정의 반영량을 조절하자 내부 Validation 점수는 높아졌지만, 실제 제출에서는 기준 모델보다 성능이 낮아졌습니다.

이 방법은 최종적으로 채택하지 않았습니다. 특정 연도의 월별 패턴이 다음 시즌에도 반복된다고 보기 어려웠기 때문입니다. 팀은 연도별 Temporal Validation과 경기 유형별 결과를 함께 살피며, 개선이 어느 시기와 조건에서 나타났는지를 검토했습니다. 2019~2021년으로 학습해 2022년을 평가하고, 학습 구간을 한 해씩 늘려 2023년과 2024년을 평가하는 방식이었습니다.

이후 실험을 검토할 때는 점수가 올랐는지뿐 아니라, 특정 시기의 데이터에만 잘 맞는 방법은 아닌지도 확인하게 됐습니다.

## 선수 이력에 따라 Ensemble 비중 조정

단일 모델을 비교한 뒤에는 서로 다른 예측을 결합했습니다. 고정 비율로 확률을 섞는 방식, 경기 유형과 선수 이력에 따라 비중을 달리하는 방식, 기존 예측에 작은 Residual 보정을 더하는 방식을 실험했습니다.

모델을 결합할 때도 단독 성능만으로 구성 요소를 선택하기 어려웠습니다. XGBoost는 LightGBM보다 단독 성능이 낮았지만, 두 모델이 서로 다른 오차를 보이는 구간에서는 보완 가능성이 있었습니다.

팀은 두 모델을 결합하는 조건을 바꾸어 실험했습니다. 선수 이력이 적은 구간에 XGBoost 비중을 높이는 방식은 신규 투수에서 오차가 커졌고, 이후 이력이 충분한 Regular 경기 구간에서 비중을 높이는 방향으로 조정했습니다. 모든 선수에게 같은 비율을 적용하기보다 입력 조건에 따라 조합을 달리한 것입니다.

단독 성능이 낮은 모델도 다른 모델이 놓치는 구간을 보완할 수 있었습니다. Ensemble을 검토할 때는 전체 점수와 함께 모델별 오차가 발생하는 조건을 비교해야 한다는 점을 배웠습니다.

## 제출 환경에서도 같은 예측이 나오도록 검증

실험 결과를 제출물로 옮기는 과정에서는 같은 입력에 같은 계산이 적용되는지도 중요했습니다. 입력을 한 번에 처리할 때와 한 행씩 처리할 때 결과가 달라지거나, 입력 순서에 따라 Preprocessing이 바뀐다면 실험에서 선택한 모델을 그대로 평가하기 어렵습니다.

팀은 학습 데이터에서 정한 Preprocessing 설정을 Inference에서도 그대로 사용하도록 했습니다. 데이터를 한 행씩 처리하거나 Batch를 나누거나 입력 순서를 바꿔도 예측이 일치하는지 테스트했습니다. 실험에서 얻은 성능을 제출 환경에서도 유지하려면 이런 검증이 필요했습니다.

## 결과와 배운 점

팀은 대회에서 **63위, 1,162.43634점**을 기록했습니다.

팀장을 맡으면서 팀원들의 작업을 이해해야 일정과 실험 방향도 조율할 수 있다는 점을 배웠습니다. 문서로 공유된 결과와 코드를 함께 읽는 일이 회의에서 구체적인 의견을 내는 데 도움이 됐습니다.

기술적으로는 도메인 이해가 데이터 처리와 모델 실험의 기준이 됐습니다. 선수 이력이 없다는 사실을 어떻게 표현할지, 최근 기록을 얼마나 신뢰할지, 어떤 상황에서 모델을 결합할지를 데이터의 의미와 함께 판단해야 했습니다. Feature를 늘리거나 복잡한 모델을 도입하는 것보다, 가설을 하나씩 비교하고 효과가 없는 시도를 제외하는 과정이 중요했습니다.
